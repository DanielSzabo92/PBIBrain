# Controlled local promotion and recovery

Promotion requires a candidate-bound controller-signed permit, valid contract/policy/evidence identities, all mandatory gates, separate required approvals and an unchanged baseline. The orchestrator locks each operation; the filesystem controller separately locks the destination project. Candidate contents are rehashed before writes and per file during application.

The local controller records authorized replacements, before/after hashes and backup locations in a signed durable journal before applying replacements. It uses controller-owned staging on the destination volume, so interrupted staging does not leave unclassified temporary files inside the original project. Backups remain outside original/candidate roots. Files are individually replaced; the entire multi-file operation is not crash-atomic.

Journal states are PREPARED, APPLYING, COMMITTED, PROMOTION_RECOVERY_REQUIRED and RECOVERED. COMMITTED means source bytes match the candidate manifest. Final successful operation state is POST_PROMOTION_VERIFIED only after a fresh isolated authoritative scan matches the verified candidate identity. A failed post-promotion check explicitly marks the journal for recovery, including after byte-level commit.

On failure, stop source writes and preserve the journal/audit. Run the trusted `pbi-guard recover OPERATION_ID` with the same source/state/project configuration. Before restoring anything, recovery verifies every backup and verifies that each current target matches a journal before/after hash. Unrelated concurrent edits, corrupt backups, missing evidence or unsafe paths block recovery. Restore files in reverse order, verify the entire original manifest, and mark RECOVERED only after verification. Restarting the controller does not erase recovery state.

Recovery is repeatable after a partial restoration. A committed journal without a requested recovery is inspection only; newer source edits are never silently rolled back. The prior state remains available, but successful rollback is not reported without matching hashes. Fault fixtures cover interruption after a file replacement, restart, corruption, concurrent changes and failure of post-promotion verification; abrupt termination at every OS write boundary still needs a broader fault matrix.

The Git helper creates an isolated review revision with a temporary index and a `refs/pbi-guard/...` reference, preserving HEAD/index/worktree and baseline parent. It does not push, deploy or promote authoritative Git history. Integration of Git promotion/ref rollback with the orchestrator journal remains unfinished. Use the implemented guarded local flow only after required evidence succeeds; do not treat creation of a review revision as promotion.
